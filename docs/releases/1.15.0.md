# Point it at a name and it works out the rest

Give Hypergate a server's registry name and it resolves that name to one pinned server, with the exact command to run it and a plain list of what running it will take from you. Agents can ask for one; you decide.

### Features

- **Resolve a name to a ready-to-add server.** `com.microsoft/azure` resolves to `npx -y @azure/mcp@2.0.2 server start` — Microsoft's own documented invocation, worked out from registry metadata with no Azure-specific code anywhere. Fully-qualified names go straight to that server's version history, which is both authoritative and quick.
- **A setup plan, not just a command.** Resolving also answers *what this will need from you*, as ordered steps checked against your machine: the runtime it needs, the credentials it needs (with the vendor's own link for getting one), a browser sign-in, or a sign-in that belongs to another tool. Steps you already meet are marked done, so a server you are ready for says so.
- **Install and sign-in are treated as separate questions.** The registry says how to *run* a server and almost nothing about how to *authenticate* one — Azure and GitHub's own server both publish an empty list of environment variables, and neither works without credentials. Hypergate fills that half from what it already knows: Azure needs `az login`, GitHub needs a personal access token.
- **Ambiguous names are questions, not guesses.** Asking for `azure` returns the twelve servers that could mean, rather than picking one. An exact name always wins outright, so `com.microsoft/azure` can never quietly resolve to `com.microsoft/azure-devops`.
- **An agent can ask you to add a server.** When an agent needs an MCP server that isn't set up, it can now resolve it and ask, instead of telling you to go and edit a config file. The request appears in the MCP servers section with what the agent wanted it for, the exact command that would run, and anything it will still need afterwards. **Add & approve** adds it and starts it. Agents never add servers themselves.
- **The MCP servers tab tells you someone is waiting.** A pending request shows as a count on the nav item, the way credential and tool requests already do, so you find out without being on that page.

### Bug fixes

- **Registry search no longer installs stale versions.** Results were pinned to each server's *oldest* published release — every single multi-version server in the registry, because the rows arrive oldest-first and the old code kept the first one. Searching now gets you the newest stable release.
- **Hosted servers can be added.** Three quarters of the registry publishes a hosted endpoint rather than a package, and all of it was listed as "not locally runnable yet" even though Hypergate has been able to connect to remote servers for many releases. Those servers now connect like any other.
- **A beta is not the latest.** The registry's own idea of "latest" for Azure is a `3.0.0-beta.37`; Hypergate picks the newest stable release instead, and takes a prerelease only when asked.
- **Platform binaries are matched to your machine.** A server that ships one binary per operating system is only offered when one of them is built for yours, instead of resolving to a download that cannot run.
