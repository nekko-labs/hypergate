# Hypergate — Spec

> **Source of truth for *what* Hypergate is and *why*.** The *how* (stack, architecture, conventions, backlog) lives in [`TASKS.md`](TASKS.md). Living document: every shipped feature gets a status + release-version entry here; new work is broken down in `TASKS.md` first.

## 1. Vision & Positioning

**Hypergate** (formerly NekkoMCP; renamed 2026-07-25, home: [hypergate.app](https://hypergate.app)) is an **open-source, local-first runtime and manager for MCP (Model Context Protocol) servers** — a ToolHive rival you actually own. It securely runs MCP servers, supervises them, and exposes them through a single gateway endpoint that any agent harness (Claude Code, Cursor, **Kotrain**, Codex, VS Code) can connect to.

It is **not just a connector list** — it is a proper MCP *server runtime*: it launches servers, isolates them, manages their secrets, watches their health, and aggregates them.

| It rivals | …and wins by |
| --- | --- |
| **ToolHive** (Stacklok) | Fully local-first and free, **no Docker requirement** (Docker is opt-in, not mandatory), with a beautiful built-in UI and a one-paste gateway URL. Self-host the registry/gateway; nothing phones home. |
| **Docker MCP Toolkit** | Doesn't require Docker Desktop; runs servers as sandboxed processes by default; cross-platform. |
| **MetaMCP / MCPHub** | A real supervisor with isolation + secrets + health, not just a proxy; first-class agent-harness integration; a polished UI. |

**Two faces, one engine:**
1. **Standalone app** — its own UI (served by the daemon; Electron later) to add, configure, run, and monitor MCP servers; rivals ToolHive's portal.
2. **First-class Kotrain integration** — Kotrain (already an MCP *client*) auto-detects the daemon, connects the gateway in one click, and opens this manager in a workbench pane. (Shipped natively in the kotrain repo (then open-paw) against the daemon API; the `@hypergate/ui` embeddable-package idea is parked unless a deeper embed is wanted.)

**The four feelings we sell:**
1. **Secure by choice** — pick your isolation at setup (containers *or* sandboxed processes); we make the tradeoff explicit, never force Docker.
2. **One endpoint** — run many servers, expose one gateway URL; paste it into any harness.
3. **Yours, local, free** — open source (MIT), nekko-labs org; runs on your machine, no account required.
4. **See everything** — routing through one gateway means a free, private audit trail: which tool, called by which client, how much data — visible in the Analytics tab, never leaving the machine.

### Isolation model (user-selectable at setup)

Hypergate lets the user choose the runtime per install (and per server override). We surface the tradeoffs plainly:

| Runtime | Isolation | Pros | Cons |
| --- | --- | --- | --- |
| **Process sandbox** (default, no deps) | Child process: scrubbed/allow-listed env, injected secrets only, restricted CWD, no shell. With the desktop shell installed, also OS-enforced resource limits and reliable process-tree teardown (see the limits table in §3.1) | Zero dependencies, instant start, cross-platform, lightest; great for solo/local dev | Weaker boundary than a container (shares the kernel/user); a malicious server has more reach than in a container. Network-egress allow-listing is not implemented yet (§3.1) |
| **Docker container** (opt-in) | Container-per-server: image pinned, read-only rootfs where possible, dropped caps, network policy, CPU/mem limits, secrets via env/files | Strong isolation + reproducibility + audit; ToolHive-grade | Requires Docker installed/running; slower cold start; heavier on resources |
| **Remote** (hosted) | No local process at all: the gateway holds an HTTP/SSE client to a provider's hosted MCP endpoint, authenticated with OAuth. Isolation is the provider's problem; the credential is an OAuth token stored locally, never a spawned command | Nothing to install or sandbox; official first-party servers (GitHub, Context7, …); one-click browser sign-in | Trusts the provider; needs network; the server's behavior is out of our hands |

Default = **process sandbox** (works everywhere); **Docker** for container isolation; **Remote** for hosted first-party servers. The choice is a setup step and overridable per server.

### Scope boundaries (deliberate)
- **Local-first**: the runtime + gateway run on the user's machine; no account or cloud required. The daemon makes no outbound calls **on its own**; the only network traffic is user-initiated: **registry search** (while the user types a query, never on boot), the **CLI lookup** (the npm registry plus Homebrew's formulae API, likewise only while the user types), **catalog popularity** (npm downloads + GitHub stars, fetched only when the user opens the catalog and cached 24h — never on boot), the **update check** (npm registry, else the GitHub release, only when the manager is opened or the button is pressed, cached 24h; it sends nothing about you, so it is a lookup rather than telemetry), and **remote servers** the user adds — connecting to their hosted MCP endpoint plus the OAuth login/token exchange for those that need it. OAuth tokens and the gateway token are stored in the **OS keychain** (Credential Manager / Keychain / Secret Service), falling back to `~/.hypergate/` where no keychain exists; nothing phones home. CLI detection is fully local (a shell-free PATH scan, no network).
- **No accounts, no billing, no control plane** (decided 2026-07-27). Local-first with no sign-up *is* the differentiator against ToolHive, so we are not trading it for a revenue line: there is no identity, no entitlement check, and no hosted tier. Usage metering exists solely so the user can see their own traffic, and it never leaves the machine. Revisiting this would mean revisiting the whole positioning above, not just adding a feature.
- **Harness-agnostic**: we expose a standard MCP gateway (stdio + streamable HTTP/SSE) so *any* client works; we don't lock to Kotrain.
- Not a hosted SaaS registry (we ship a curated catalog + custom server config; community/registry sync is later).

## 2. Users & Core Journeys
- **Agent power-user / developer**: "I have 6 MCP servers (filesystem, github, postgres, my vault, …). I want them running safely and reachable from Claude Code via one URL — without hand-editing JSON per client."
- **Kotrain user**: "Manage my MCP servers in a tab, toggle them on/off, see their tools and logs, and have my agent use them."
- **Privacy/security-minded**: "Run untrusted community MCP servers in a container so they can't read my whole disk."

Journeys: add a server (from catalog or custom command/image) → choose runtime → start → see status/tools/logs → copy the gateway URL → the agent uses the aggregated tools. Toggle, restart, edit secrets, stop.

### 3.1 Server runtime & supervisor `[shipped]`
| Feature | Description | Status | Release |
| --- | --- | --- | --- |
| Process runtime | Spawn a stdio MCP server as a sandboxed child (allow-listed env, injected secrets, restricted CWD, no shell); capture logs; health/restart | shipped | v0.1.0 |
| OS-enforced resource limits | A per-server `limits` block (`memMb` / `cpuPct` / `nofile`) is applied by spawning through `hypergate sandbox-exec`, which Node cannot do itself. stdio is inherited, so the MCP stream is unaffected. Also fixes leaked grandchildren: killing an `npx` shim on Windows previously left the real `node` running. When the shell is absent the server starts unsandboxed and the log says so explicitly, rather than implying limits are in force | shipped | v0.8.0 |
| Network-egress allow-list | Restrict which hosts a managed server may reach (Windows Filtering Platform / nftables per-process rules). Not implemented; the isolation table in §1 is careful not to claim it | planned | later |
| Docker runtime | Container-per-server (opt-in): pull/run image, env/secrets, caps/network/limits | shipped | v0.1.0 |
| Remote runtime | Connect to a hosted HTTP/SSE MCP endpoint (no child process). The supervisor holds a `StreamableHTTPClientTransport` (or SSE) with an OAuth provider that attaches + refreshes the bearer token; a token-less server sits in a new `authorizing` state instead of erroring | shipped | v0.5.0 |
| Supervisor | Start/stop/restart/remove, status (starting/ready/errored/stopped), structured logs ring-buffer. A server you stopped stays in the roster rather than disappearing: the daemon seats disabled configs with `Supervisor.register()` at boot, so it is still listed (and startable) after a restart, fixed in v0.11.1 | shipped | v0.1.0 |
| Crash backoff | Auto-restart with backoff when a running server dies | planned | v0.3.0 |
| Secrets in the OS keychain | The gateway token and every remote server's OAuth grant live in the OS keychain (Windows Credential Manager, macOS Keychain, Linux Secret Service) via the shell binary, replacing plaintext files under `~/.hypergate/`. One keychain entry per server holds the whole grant blob, cached in memory, so a boot costs one subprocess per remote server rather than one per key. Existing plaintext files are migrated on first read and then deleted. Falls back to the previous file behaviour where no keychain exists (e.g. headless Linux with no Secret Service) | shipped | v0.8.0 |
| Per-server secrets in the keychain | Managed servers' own `secrets` (injected env) still live in `servers.json`; move them into the keychain too | planned | later |
| Stop on request (graceful) | `POST /api/shutdown` takes the daemon down on purpose: it stops listening, closes every managed server (their children are ours, so exiting without that leaks a process tree), flushes the usage store and exits 0, answering the caller *before* it goes, so the UI can say it worked. Guarded twice, because the management API answers with a wildcard CORS header: the **master** gateway token (an agent's scoped token may call tools, not kill the runtime) and a **same-origin** check, so no page the user happens to visit can reach in. Server `enabled` flags are untouched, so a restart brings everything back. The shell's `hypergate stop` keeps its pid-file path, which needs no token and still works when the daemon is wedged | shipped | v0.11.0 |

**What each limit actually does, per platform.** Nothing here is aspirational: `--strict` turns an unappliable limit into an error rather than a silent no-op, because a sandbox you believe you have is worse than none.

| Limit | Windows | macOS / Linux |
| --- | --- | --- |
| `memMb` | Job Object `JobMemoryLimit` | `RLIMIT_AS` |
| `cpuPct` | Job Object CPU rate hard cap | not applied (needs cgroups v2 delegation) |
| `nofile` | not applicable (no per-process fd table) | `RLIMIT_NOFILE` |
| process-tree teardown | `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` | dedicated process group |

### 3.2 Gateway `[shipped]`
| Feature | Description | Status | Release |
| --- | --- | --- | --- |
| Aggregating MCP gateway | One MCP endpoint that fans out to all running servers; tools namespaced `server__tool`; routes calls to the owning server | shipped | v0.1.0 |

| Per-client tokens + allow-list | Named **connected agents**, each with its own gateway token scoped to a per-server allow-list (`'*'` or specific servers). The gateway hides disallowed servers from `tools/list` and refuses their `tools/call`; the master token keeps full access. Calls are attributed to the agent's name in analytics. Managed at `/api/clients` + the UI's "Connected agents" section. Granularity is per-server (not per-tool) by design | shipped | v0.4.0 |
| Enable/disable a server per agent | The allow-list is a one-click switch instead of a form: `POST /api/clients/:id/servers/:serverId` flips one server for one agent, and the live gateway reflects it on the next `tools/list`. The daemon owns the arithmetic because only it knows the full roster: turning a server off for an `'*'` agent **pins** that agent to the servers configured right now (there is no way to say "all but this one"), and the UI says so; enabling never silently widens a list back to `'*'`. Revoking a server that no longer exists is always allowed, so a stale entry can be cleared; granting one 404s | shipped | v0.11.0 |
| In-place agent token rotation | `POST /api/clients/:id/token` mints a replacement credential without changing the agent's name, target or server scope, so a leaked token can be revoked without rebuilding the client | shipped | v1.0.2 |
| Credentials a client fetches instead of storing | Connecting used to copy a token into a client's config, where it sat until the token rotated or the agent was re-created and the client was simply broken with no way to know. For clients that can run a command at connect time (Claude Code's `headersHelper`), the config now names `hypergate mcp-headers <agent>` instead, which resolves the agent — by id, by name, or by the stem of an id that no longer exists — and prints its bearer token. The daemon only writes that form after running the command here and seeing real headers come back, because a helper that isn't there is worse than a token that might go stale. Every other client keeps the token, `.mcp.json` included, since it is read by harnesses that would choke on a field they don't know | shipped | v0.18.0 |
| stdio proxies to the resident daemon | `hypergated --stdio` used to start its own copy of every enabled server, so each harness that spawned one ran a private fleet. It now probes `/health` and forwards `tools/list`/`tools/call` to the running daemon's `/mcp` when there is one, leaving namespacing, permissions and usage recording where the servers live; with no daemon it starts them itself exactly as before (`HYPERGATE_STDIO_PROXY=0` forces that). `HYPERGATE_STDIO_AGENT=<key>` makes the spawn identify as a scoped agent rather than use the master token | shipped | v0.18.0 |
| Resources & prompts aggregation | Aggregate `resources`/`prompts` alongside tools | planned | v0.3.0 |

### 3.8 Desktop shell & CLI `[shipped]`

`apps/shell` is a single Rust binary, `hypergate`, that is the product's desktop presence. It is a **per-user logon agent, never a system service**: managed MCP servers need the user's `PATH`, home dir, npx cache, per-user Docker socket and keychain, none of which a SYSTEM/root service has (and on Windows, Session 0 isolation would kill any UI). Settings → Updates renders the same state from the same hook, so the two surfaces cannot disagree | shipped | v0.15.0 |
| Download now, install later | The daemon downloads the update itself and stays up while it does, because nothing it is running from is touched until the install. That is what makes **Download only** a real choice rather than a delayed apply: the packages land verified in `~/.hypergate/updates/<version>/`, the topbar then offers **Install & restart**, and that install is a local file operation with no network. Progress is real bytes out of a real total (a GitHub release states each asset's size; an npm packument doesn't, so a HEAD fills it in). Everything is checked against the hash the feed published before it is allowed to count as downloaded, and a payload may only be fetched over TLS or from loopback | shipped | v0.15.0 |
| Release asset integrity | GitHub release tarballs are checked against the release's SHA-256 manifest before staging, matching the npm feed's integrity checks; assets without a usable checksum are refused | shipped | v1.0.2 |
| Updating without npm | The update payload is the same two npm packages either way (`hypergated-‹v›.tgz` plus this platform's `hypergate-shell-‹os›-‹arch›-‹v›.tgz`), and the release attaches both. So the feed that answers decides where they come from: the npm registry when the package is published, **the GitHub release's own assets when it isn't** — which is what lets Hypergate update itself before anything reaches npm. The install is `npm install -g` over the downloaded files either way. The release job packs the tarballs whether or not an `NPM_TOKEN` is configured, and publishing is skipped rather than fatal when it isn't | shipped | v0.15.0 |
| Saying how it went | The updater records the outcome to `~/.hypergate/updates/last-result.json` before it relaunches, and the version that comes up reports it once as **✓ Updated to v‹x›** and clears it. Without that, a successful update is indistinguishable from a crash and a restart. A failed one surfaces as **Update failed** with Retry, and an install that never took the daemon down (so the daemon is still there a minute later to notice) is reported as failed rather than left spinning | shipped | v0.15.0 |
| Skip a version | **Skip** stops a version being offered in the topbar without pretending it isn't there: Settings still shows it with **Un-skip**, and pressing Check for updates spends the skip, because asking means you want to know | shipped | v0.15.0 |
| Signed update feed (auto-update) | Auto-download-and-run the **signed** native installers, so the installer channel updates in one click too. Blocked on Windows/macOS signing (docs/signing.md) | planned | later |

The promise is **one command to a working gateway**: a user installs Hypergate and runs it, never a repo checkout, an `npm install`, a build step, or a Rust toolchain.

## 4. Design System & Considerations
**Hypergate brand (v0.7.0, the rename era): the warp gate.** Deep-space near-black (`#05060f`), the violet→cyan gradient (`#6d5efc` → `#22d3ee`) reserved for the gate ring and key accents, ice (`#a5f3fc`) for the core. The mark is a gradient ring with a glowing core (favicon, tray icon, splash, site), and every surface now draws the *same* ring: the site's WebGL hero, the app's rotating conic mark in the topbar, the static favicon, and the procedurally rendered tray/window icon. The gate stands for speed, security, and connecting MCP worlds through one aperture. In-app: two themes toggled by one sun/moon button in the topbar and driven entirely by CSS custom properties on `<html data-theme>`: **Dark** (the shipped default, a calm mid-slate) and **Light**; the choice is persisted and applied before paint (no flash), and switching reveals the new palette as a circle expanding out of the button. The look is deliberately de-boxed: hairline-divided lists over stacked bordered cards. Still reads as a sibling of Kotrain and Nekko Notes (same palette era, Nekko Labs family). Status pills: ready=success, starting=warning, errored=danger, stopped=muted. Logs are monospace, capped ring-buffer. Marketing site type: Space Grotesk display, Inter body, JetBrains Mono code.

## 5. Technical Architecture & Decisions (with the *why*)
See [`TASKS.md`](TASKS.md). Key decisions: TypeScript + npm workspaces (match the org stack so the UI can be shared with Kotrain); a long-running **daemon** (`hypergated`) as the runtime + management API + gateway; a **RuntimeAdapter** interface with `ProcessRuntime` (default) and `DockerRuntime` (opt-in) so isolation is pluggable + user-selectable; the gateway built on `@modelcontextprotocol/sdk` (client per managed server ↔ one aggregated server). Local-first, no account.

**Two languages, split by what each is actually good at** (v0.8.0, see [`TASKS.md` §1.1](TASKS.md#11-stack-amendment-2026-07-27)): the **Rust shell** owns everything that needs native OS APIs (tray, login items, keychain, Job Objects / `setrlimit`), because `windows-rs`, `objc2` and `zbus` make those ordinary dependencies rather than hand-written FFI. The **TypeScript daemon** keeps all the MCP protocol work, where the official SDK lives and moves fastest. Durable state is **SQLite** via `node:sqlite`, chosen over `better-sqlite3` specifically to avoid a native addon inside a binary that has to be signed and notarized. Rejected: Flutter and React Native (UI toolkits, not service runtimes; RN has no Linux desktop target), Electron (150MB resident for a dashboard of tables and logs), and full Tauri (its config/IPC layer buys nothing here). The manager window (v0.10.0) uses **wry directly** (the same webview crate Tauri wraps, joining the `tao`/`tray-icon`/`muda` family already in the shell), so the desktop app renders the OS's own webview (WebView2 / WKWebView / WebKitGTK) and the binary stays ~3MB.
